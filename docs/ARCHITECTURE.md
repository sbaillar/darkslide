## Pipeline staging (why warm renders are cheap)

```
RawImage ──► [BASE]  black/white norm → reference (as-shot) WB → demosaic (superpixel or RCD)
                     → pyramid level for the view. Camera RGB, f16 (previews) / f32 (Full).
                     Cached per (ImageKey, level); one entry per level, replaced (not added)
                     when a pan/zoom leaves its rectangle.
          ──► [DEVELOP] geometry (crop/rotate/flip, keystone homography, lens distortion + TCA)
                     folded into one bilinear resample (2×2 supersampled for settled views) →
                     heal/clone spots → WB ratio (user / reference) → highlight reconstruction →
                     lens vignetting → camera matrix → exposure / vignette → gamut compress →
                     lens blur → dehaze → HDR (guided-filter local tone) → profile maps → hue-preserving tone curve →
                     levels / curves → color balance → saturation → vibrance → color editor →
                     clarity / structure / texture → layers (masked; every global tool except
                     crop, lens and NR) → glow / halation → NR (ISO-adaptive) → sharpen →
                     grain → [export: resize in linear light + output sharpening] → output
                     transform
                     (sRGB / Display P3 → RGBA8, RGB16, or linear P3 f16) [+ histogram]
```
- **White balance, exposure and everything else are DEVELOP work**: a WB drag never rebuilds the BASE (the BASE is at the reference WB; DEVELOP applies `diag(new/ref)` and reconstructs highlights with the user's clip). Only a new image, a new pyramid level, or a pan outside the cached rectangle rebuilds it.
- Views demosaic like the export (**RCD** plus box-downsampled pyramid levels, 2×2-supersampled when a level is sampled at a step ≥ 1.25), so a settled view and the export of its size show the same noise; only thumbnail-sized renders (scale ≤ 0.15) use the 4× cheaper **2×2 superpixel** demosaic. 1:1 regions demosaic only the sensor bounding box of the view (+16 px margin, +25% pan slack); RCD reads real neighbours outside the box, so a region equals the same pixels of a full-frame demosaic.
- **Region (tile) renders are seamless**: they develop with an apron sized to the neighbourhood filters' reach (HDR, clarity, structure, NR, sharpen, mask feather; ≤ 1024 px) and anchor the guided-filter block grids to the full frame, then output only the window. Quadrant tiles match a full render at ΔE2000 mean 0.000.
- The CPU renderer is the **reference implementation**. The GPU renderer must match it within **ΔE2000 ≤ 0.05 mean / ≤ 1.0 p99** (`tests/gpu.rs`, whenever an adapter is available).
- WB `Custom{temp_k,tint}` ↔ multipliers uses the ds-raw convention `mults(T) = normalize(wb_daylight ⊘ (N·xyz(T)))` (Planckian locus, tint = 1/3000 Δuv), so the as-shot multipliers round-trip through K/tint.
- **Memory**: BASE caches of all renderers share one budget, physical RAM / 4 (`cache::budget_bytes`, overridable with `cache::set_budget_bytes`); oldest entries are evicted first. `evict(key)` drops only that image. The GPU renderer keeps ≤ 3 RAW uploads and trims its buffer pool after large exports. On the GPU the budget is a **hard ceiling**: every allocation (BASE levels, frame-pool buffers, output slots, RAW uploads, mask rasters, export stripes) is accounted by use (`cache::used_by_use`), makes room first (stale pool buffers, other images' RAWs, rasters and BASE levels), and renders are admitted by a memory gate that waits for room instead of exceeding it (a render alone is always admitted). `cache::peak_bytes` is tested ≤ the budget under an 8-thread thrash plus a background export (512 MB: peak 483 MB).
- **Brush masks** are rasterised in the image ("E") frame at ≤ 3072 px long edge, incrementally (only new stamps), cached per (image, layer, shape) and uploaded to the GPU by dirty rows; views sample them, so crop/zoom never re-rasterises.
- **Interactive drags** request `Quality::Draft`: the same BASE as `Preview` (no rebuild when a drag starts), developed at ≤ 2048 px long edge (`DRAFT_LONG_EDGE`; 1536 for heavy edits, `plan::draft_long_edge`: several masked layers with local tools and output-space mask planes over a busy global edit) and bilinearly upscaled to the requested size without sharpening; request `Preview` on idle for the full-resolution refine. (5K fit, 2832 px: every drag p90 ≤ 10 ms in the pipeline; every step-3 tool ≤ 10.6 ms, `benches/render.rs` `develop_tools`.)
- **Scheduling on the shared `GpuRenderer`**: CPU preparation (plan, mask rasters, RAW staging) runs outside any lock; GPU work is recorded and submitted in short turns and the readback wait happens after the turn. Each turn goes to the highest `Priority` class waiting — `Interactive` (viewer) > `Tool` (auto tools, pickers) > `Background` (exports, prefetch) > `Bulk` (thumbnails); each non-interactive class has one render in flight (FIFO within the class; the wait honours `cancel`) that yields between stages, so a thumbnail storm never delays auto tone or an export by more than a stage (64-thread storm: auto tone +8 ms, export +28 ms). Non-interactive renders are admitted only with a quarter of the memory budget free. Readback waits poll with a short backoff (100 µs, then 2 ms).
- **Threads and locks**: the CPU-parallel parts of renders (planning, lens maps, mask stamping, tiles) run on ds-pipeline's own rayon pool (`par::run`); non-interactive CPU renders use a half-core pool (`par::run_low`). No lock is ever held across parallel work: every pipeline lock goes through `par::hold`, and entering a pool with one held is a debug assertion (a worker waiting for its parallel work may steal another render's job that needs the same lock). The one exception is the GPU renderer's own lock (`gpu::Inner`), held while a linear image is converted into its BASE: that work runs on the pipeline pool (`par::run_holding_renderer`), whose jobs never take that lock. A GPU render never runs parallel work on the caller's pool (rayon's global pool in the app) while it holds its background slot or the renderer lock: that pool's workers may all be renders parked on that slot or lock (`tests/gate_deadlock.rs`). The CPU renderer is `Clone` and shared (caches locked only for lookups), so a viewer never waits for an export on the CPU fallback either. Large `Full`/background outputs render as seamless 2048 px tiles and the BASE demosaic runs in ~4 Mpx bands, each stage waited for before the next is submitted, so a cancel or an interactive frame waits for at most one stage. Interactive and background work keep separate frame-buffer pools. The interactive image's RAW upload is pinned. `GpuRenderer::prefetch` builds the next pan rectangle in the background.
- **GPU does the analysis too**: the display histogram is binned in the output pass (`RenderRequest::histogram`, `Renderer::render_frame_into`); `GpuRenderer::auto_white_balance` / `auto_levels` take their statistics from the resident mosaic (so `key` must identify the raw: two raws under one key get the first one's answer) and a GPU probe render. Auto WB trusts the as-shot setting unless the image shows it wrong: a dense multi-luminance neutral cluster far from as-shot, or the white patch's cluster (≥ 8% of the weight, one luminance is enough: a gray card, fog) lying on the Planckian locus at 2400–9000 K; otherwise a gray world weighted toward the locus (broad toward warmer light, narrow toward cooler, where blue sky lies), clamped to ±600 K / ±10 tint. Resized exports develop at **full resolution** in 1024 px tiles and full-width stripes (output-transformed, 16-bit fixed point), are resized on the GPU per stripe (area-correct Catmull-Rom, linear light; horizontal pass per stripe, vertical pass at the end), then `RenderRequest::output_sharpening` is applied at size — ds-export never resizes on the CPU. Tone matches a Lanczos3 downscale of the full render (chart ΔE2000 mean 0.07); background turns stay ≤ ~8 ms, so a viewer keeps p90 ≤ 20 ms during a 4000 px export. The CPU renderer implements the same stages as the reference.
- **Device loss**: the device is polled before every turn; scope/map errors or a panic inside a turn mark it *suspected* lost; the next turn verifies (lost callback, or a probe that writes and clears a tiny buffer — a destroyed device still hands out invalid buffers) and rebuilds exactly once per real loss, dropping every resource and output slot of the lost generation (epoch-checked; a render never returns Ok with stale pixels). Real `device.destroy()` under 8 threads is tested.
- **Presence**: vibrance (saturation weighted toward muted colours, skin tones protected), texture (a fine band-pass: a guided plane with ε ≈ (10 %)², so texture-sized contrast is detail and only real edges stay smooth; +100 multiplies it by up to 2.75 above the measured noise, −100 removes it) and dehaze. Dehaze estimates the haze from a patch dark channel (block-mean dark channel relative to the atmospheric light, min-filtered over 3×3 blocks, ~1% of the long edge) refined by a luminance-guided filter; the light is the mean of the 0.1% brightest-dark-channel blocks without clipped samples, measured once per image. Positive recovers luminance only (hue kept) with a transmission floor of `1 − (0.6 + 0.25·haze)·k` (lower where the haze estimate is confident), a veil capped at 0.6 of the neighbourhood's edge-aware mean luminance (one bounded subtraction per neighbourhood, so dark land gains contrast instead of clipping), He et al.'s `t ≥ K/|Y/Y_A − 1|` near the light, protection of bright, light-coloured, smooth regions (clouds, white water: the prior can't tell them from haze), a local-contrast term (luminance against its edge-aware ~1% neighbourhood mean, raised to `1 + k·(0.3 + 0.7·haze)`: Lightroom's dehaze punch), and a bounded OKLab saturation gain for muted colours that never leaves sRGB. Negative adds a veil in proportion to the haze estimate (10–40% of the way to the light). Layers carry them too, plus local sharpening (a 5-tap Gaussian high-pass whose σ is 0.015% of the long edge, so a fit view shows about what the downsampled export has; the gain above the measured noise; negative softens: fine detail and texture removed) and HDR whites/blacks. Each neighbourhood plane (HDR, clarity, structure, texture, haze) is built only when something uses it; identity costs nothing.
- **Masks**: shapes (fill, linear/radial gradients with their handles, colour range, brush, AI) combine with add/subtract/intersect, then feather, invert and luma/colour-range refinement. Brush and AI shapes may carry their own feather (their E-frame raster is blurred, cached); colour ranges and auto-masked brush strokes are output-space planes built per render. A colour range is refined edge-aware: its weight is guided-filtered on a guide of luma + 0.35 × a soft version of its own hue weight (radius ≥ 0.2% of the long edge, or ~1.7σ of its feather), so the key is smoothed within a surface and its feather spreads only over similar tone and colour, never as a halo onto the background; the filter's coefficients are applied to the guide after a 5×5 bilateral smoothing (range σ 0.2), so the guide's pixel noise doesn't come back as speckle. Auto-mask keeps only the tones and colours found under the strokes' centre line (core-weighted local reference of luma and OKLab a/b, `exp(−(ΔY/0.08)² − (Δab/0.06)²)`), so a stroke overlapping an edge stays on its side; the reference neighbourhood is half the brush size in normalized units (≤ 3% of the long edge), the same at every scale. Output-space feathers (whole mask, colour range, auto-masked brush) stop at `MAX_PLANE_FEATHER` = 5% of the long edge (ds-core sanitizes to it, the pipeline clamps too): a region or export tile renders with that much context (apron), so tiles and 1:1 views match the full frame. AI targets (subject, sky, person, background, and the people sub-parts face, skin, eyes, teeth, hair, clothes) come from the app's `MaskSource`; a people target may name one person (`MaskShape::Ai::person`, index in the app's largest-first order; `None` = all people), served by `MaskSource::ai_person_mask`.
- **Heal / clone spots** (`Adjustments.spots`) act on the camera-linear samples before everything else: the source disc is sampled through the full geometry; clone blends it in, heal multiplies its texture by a smooth gain from 8-sector rings around destination and source (tone and colour from the destination's surroundings). The source disc is pinned inside the E frame and source reads clamp to the sensor edge (never black). Ring statistics are trimmed means of the on-image samples; the gain is a bounded luminance ratio (0.25–4) times a bounded chroma correction (0.87–1.15), interpolated between sectors in log space and eased by rho² toward the whole-ring gain. There is no spot cap: spots are binned into 32-pixel output tiles (`spots::bins`, uploaded after the spot data on the GPU), so every path renders every spot. A region's BASE box grows to cover spot sources, so tiles match the full render.
- **Content-aware removal** (`Adjustments.removals`, `ds_pipeline::removal`): each removal's strokes (corrected E frame) are mapped to the sensor through the render geometry and rasterised (grown 2 px, feathered) tile by tile (768 px tiles, each capsule over its own span only); the fill runs in windows, decided per cluster of touching footprint tiles (dust apart from an object is its own cluster): one around an object (½ of the footprint's size of context each side, square where the frame allows), or, for a long thin stroke (longer than two tiles and thinner than half a tile: covered px per px of length), one window per tile with 192 px of context, in order, each seeing the earlier windows' fill as known and the later ones' hole as unknown (so a stroke across the frame fills at about the engine's native resolution with a few MB per window). A window over 2048 px (a big object or a wide stroke) is never worked at full resolution: the engine fills a ≤ 1536 px box-averaged image of it (demosaiced band by band), and each footprint tile is finished from the upsampled fill (detail transfer from one pool of ≤ 512 known blocks sampled over the whole window, so inner tiles of a big object are as textured as edge ones; grain); a 61 MP budget test keeps every case under 1 GB peak RSS; footprint coverage is stored as u8. Each window is RCD-demosaiced at full resolution, turned upright, encoded to display RGB (invertibly: a highlight roll-off instead of a clip, and a global desaturation for out-of-gamut colours undone on decode) and filled by the app's `Inpainter` (Core ML LaMa, 800 px) or the built-in exemplar fill (onion peel with a PatchMatch search, 768 px, `ds_pipeline::inpaint`); the fill is upscaled, un-tone-mapped, given the texture band the engine's resolution lost (luminance band-pass blocks from the known area, chosen by tone) and **re-mosaiced into the RAW** with synthetic sensor noise (per-colour `σ² = a·v + b` fitted on the crop, capped by the frame's measured shot noise), blended over the feather. So every later stage (BASE pyramid, crop, straighten, develop) sees the fill as photo, on the CPU and the GPU, at every zoom, with the camera's grain. Each removal's result is its `Patches` (final RAW samples of the sensor rectangles it changes, per tile) cached per (image, removal chain hash) in memory (256 MB) and on disk (`set_cache_dir`; least recently used deleted beyond 4 GB, at startup and after each write); the hash covers every removal up to it, the inpainter id, the stroke geometry (lens, keystone, orientation) and `PIPELINE_VERSION`, so exposure/crop/layer edits never recompute and an edited removal recomputes itself and the ones after it. Renders use a derived RAW and `ImageKey` (≤ 3 kept); concurrent renders of a new chain compute it once (a waiting render still honours its cancel); `evict(key)` drops the derived images too. Disk thumbnails of edits with removals are keyed by the engine as well (`ds_cache::render_hash`), so LaMa arriving re-renders them. The auto tools (WB, levels) measure the RAW without removals. Removals are applied before spots. Copy/apply carries them in the opt-in Spots group. (Waterfall sample, M4 Pro under load: a person removal's fill 0.4–2 s with the fallback, LaMa ~0.8 s inference; cached renders unchanged.) **Licence:** big-lama's weights are Apache-2.0 but were trained on Places365 (non-commercial research and educational terms): LaMa is downloaded on first use, never bundled (Acknowledgements).
- **People sub-part masks** (app, `AI/People/`): Vision person instances (largest first) and face landmarks, plus BiSeNet face parsing (Core ML, MIT weights trained on CelebAMask-HQ, whose licence is non-commercial, so it is never bundled; downloaded on first use, pinned by commit and SHA-256, compiled per revision, runs `.cpuAndGPU`) on an upright face crop, sampled from a high-resolution render of the face's region (the RAW, as shot, oriented frame) when the analysis image would be upscaled for the parser; results made without the parser (colour fallback) or without the render are made again once those are available; skin on the body from a colour model calibrated on that person's face skin; clothes = person − skin − hair − face. Masks are E-frame bitmaps with versions, per person or all people. Each person-indexed shape's person is stored with its box (`Adjustments.person_boxes`, normalized), and re-matched by overlap when Vision orders people differently (OS update, thumbnail instead of preview); a person not found any more renders empty with a one-time notice in the viewer. A per-person mask that can't be made fails that photo's export with a message (never an empty layer). **Known limitations:** long hair and braids down the back are not followed (the face crop ends at the shoulders); hair is missed when the head isn't upright near the face (e.g. a diver); small or distant people aren't found by Vision (no masks); people who overlap may be merged into one instance; teeth are untested on a real open mouth.
- **Noise reduction**: chroma NR is a self-guided filter per chroma channel whose strength comes from the RAW's measured noise (`raw_noise`: MAD of same-colour diagonal differences, 20th percentile over 64 px blocks) and fades out on clean frames, so subtle colour texture survives (≥ 75% through ISO 4000) while real chroma noise is removed; the ISO setting scales it at most ×2.
- **Camera profiles** (`Adjustments.profile`, `ds_pipeline::profile`): a profile is a base tone curve (the tone stage's, and the curve layers re-tone through) plus optional DNG-style hue/saturation/value maps applied to scene-linear colour right before tone, in linear ROMM (ProPhoto) RGB, by (tri)linear lookup with hue wrapping (`HsvMap`, mirrored in `grade_fn.wgsl`). **Darkslide Standard** (the default for new edits) has ~12 % more midtone contrast with a deeper toe and filmic shoulder and a 90×30 map generated from an OKLCh twist (yellow/green skin rotated warm, greens warmer and calmer, deep blues kept from purple, skies a touch deeper); **Neutral** is the pre-profile look (no map; renders bit-identically to `PIPELINE_VERSION` 8) and **Vivid** is Standard with a steeper curve and +16 % chroma (skin +7 %). A sidecar without a `profile` key reads as Neutral (`Profile::legacy`, a field-level serde default); every build that knows the field writes it, so no schema bump. **Imported Adobe profiles** (`.dcp`, `ds_pipeline::dcp`) are registered in-process by BLAKE3 (the app copies them to `<support>/Profiles/<hash>.dcp` and registers them at launch); a render interpolates ColorMatrix/ForwardMatrix and the HueSatMaps in inverse temperature between the two calibrations (illuminant codes as the DNG SDK maps them, WarmWhiteFluorescent 2940 K included), the weight found as the DNG SDK does: the camera neutral of the WB multipliers through the profile's own colour matrices, iterated until it settles. It uses the forward matrix (else the Bradford-adapted inverse colour matrix), applies the HueSatMap (value index pre-exposure: exposure and baseline gain removed) and LookTable (sRGB value encoding honoured), the profile tone curve (linear → linear on scene linear, mid gray 0.18; Standard's curve when it has none) and BaselineExposureOffset. Adobe adds that offset to the raw's BaselineExposure; ARWs carry none (Adobe keeps its own per-camera value), so `BASELINE_EV` (1.18, the pipeline's calibrated camera baseline) stands in for it. Blended maps are cached per profile and weight (last 4); maps compare by a content hash; the GPU reuses the previous lookup-table buffer when its contents are unchanged. Files over 16 MB or tables over 90 × 30 × 32 entries are refused. An imported profile renders as Standard (`ProfilePlan::missing`) when it isn't registered or its UniqueCameraModel isn't the photo's camera (`profile::camera_matches`: words ignoring case, punctuation and the make; `camera_profile_fits` for the app), and so does a profile kind this build doesn't know (`Profile::Other`, kept verbatim in the sidecar so a save never downgrades it). Auto tools and layer WB deltas keep the camera's default matrix.
- **AI Optimize** (`ds_pipeline::optimize`). Proposals from deterministic rules over measurements, never from a language model, each with its reason, its measurements and a templated explanation. Measurements: the camera blocks of auto WB/tone (as-shot vs the neutral found, and which evidence; scene log-luminance percentiles), and ≤ 1024 px `Priority::Tool` probes with GPU histograms — the edit as it is (what the user sees) and a *baseline* (the proposed WB, exposure, geometry and auto tone's highlights/shadows, every look field the optimizer may set back at its default, user values kept) — scanned once, strided, for clipping (frame and sky mask), median/spread, HSV saturation, a 16 px dark-channel haze score, local contrast and the subject's brightness. Targets are absolute (camera data and baseline), so a second run proposes nothing; a field differing from its default is the user's unless a report remembers the optimizer setting it (carried forward from run to run while unchanged), a default the user restored over an optimizer value stays the user's, and user values are left alone (a clipping user exposure is pulled back only when highlights are set by hand too). A third probe renders all default-on proposals together (skipped when none of contrast, levels, vibrance, clarity or dehaze is proposed): while they clip (or crush) noticeably more than the baseline, the likeliest cause still proposed is withdrawn — for white clipping contrast, then the levels white point, vibrance, clarity, dehaze; for crushing the levels black point, contrast, dehaze, clarity — and the probe renders again; each withdrawn field gets a kept note saying how much would have clipped and why it was left out. Exposure, white balance and highlight/shadow recovery are never withdrawn (recovery only pulls tones away from the ends). The probes render the original RAW, never an AI Denoise blend: with AI Denoise on, a noisy frame's extreme percentiles read slightly wider and its local contrast, texture and haze score slightly higher than the denoised photo's, so the levels, clarity and dehaze proposals lean a little conservative (the noise rules measure the RAW anyway). Changes back toward a default are explained as such. Dehaze and a black-point move never stack (dehaze removes the veil): the black point holds when this run proposes dehaze checked, or the edit already has it. Explanations are templates; no language model writes them. Scene tags move the midtone target (night 9%, snow/beach 24%, sunset 14%), cap vibrance with faces, skip clarity on portraits, night and noisy frames, keep a sunset's or snow's colour under weak WB evidence, and skip dehaze on bright scenes. Straighten sets the angle only on a full frame (the pipeline fits it) and shrinks a user crop about its centre; lens corrections the user turned off and the sky layer are suggested unchecked.
- **AI Denoise** (`ds_pipeline::denoise`, `adj.noise.ai_denoise` / `ai_strength`). A learned denoiser, NAFNet-SIDD-width32 in float16, runs in the app on Core ML. `scripts/build-app.sh` converts it once from the pinned weights, caches it, and bundles it (`docs/DENOISE_MODEL.md`). A build without the model disables AI Denoise; renders and exports then ignore it. The GPU and the Neural Engine each run one instance in parallel. The network sees the full-resolution BASE (RCD at the reference WB), sRGB-encoded, in 512² tiles that overlap by at least 48 px: 117 tiles for an A9 frame.
  - **Stitching.** Tiles are cross-faded with linear ramps over each overlap. The ramps skip 8 px at each tile edge (zero padding), the weights are normalized, and a seam test checks the result.
  - **Tone match.** A low-frequency tone match at 64 px blocks keeps the original's local mean per channel. Without it, the model's bias tints shadows by about 2%.
  - **Clipped pixels.** Pixels at the clip after WB keep the original values.
  - **Result.** The output is linear camera RGB before WB. `denoised_raw` blends it with the original's linear image at the strength and returns a `CfaPattern::LinearRgb` raw, which develops like any RAW (same BASE as the mosaic within 16-bit rounding).
  - **Downstream tools.** The raw's measured noise is seeded as `raw_noise × ((1−s) + s·0.2)`, so chroma NR and the sharpen/texture thresholds follow the strength. The ds-ffi hook scales the luminance slider by `1−s`.
  - **Strength 0** renders the original raw itself, bit-identical.
  - **Timings (M4 Pro).** The Rust side takes ~0.5 s per 24 MP frame: demosaic+encode ~0.1 s, tile reads ~0.1 s, writes ~0.15 s, stitch ~0.25 s.
  - **Peak memory** for a job is the encoded BASE (144 MB) plus an f32 accumulator (288 MB) plus a 24 MB weight map. The output reuses the encoded buffer.
- **AI Upscale** (`ds_pipeline::upscale`, `ds_export::dng`, ds-ffi `upscale`). RealESRGAN_x2plus in float16 on Core ML, bundled like AI Denoise (`docs/UPSCALE_MODEL.md`); a build without it disables Upscale 2× and recipes resample. 256² tiles in, 512² out, overlapping by at least 24 px (468 for an A9 frame), cross-faded like AI Denoise's at 2×.
  - **New photo.** The BASE, sRGB-encoded, upscaled 2×; clipped pixels take the original, interpolated. Stitched rows are handed out as soon as every tile covering them is written and streamed into a linear DNG (`LinearRaw`, uncompressed 16-bit) whose colour tags decode to the source's `cam_to_xyz` and white balances: memory stays at about two tile rows of output. The DNG goes next to the original (`<name>-Upscaled.dng`, a free name, temp → fsync → rename), and `Session::add_derived` adds it with the source's adjustments. At most 256 MP out.
  - **Export.** A recipe with `ai_upscale` may enlarge; a size larger than the render runs the render (output-encoded) through the app's `UpscaleProvider` 2× before the resize (one more image of 4× the render's pixels).
- **Effects** (`Adjustments::effects`, `ds_pipeline::effects`; the CPU reference and the WGSL kernels `bokeh_*`, `fx_*` and `grain_*` mirror each other, `tests/gpu.rs` `effects_*`).
  - **Lens blur** runs in scene-linear light right after the scene stage (so the scene-linear path is taken whenever it is on), so highlights bloom the way a lens renders them. Each pixel gets a signed circle of confusion (negative in front of the focus) from the app's depth map (`MaskSource::depth_map`: Depth Anything V2 Small on the analysis image, the subject's edge taken from the Vision matte; the nearest of the four bilinear taps, so a subject's edge pixels keep the subject's depth) as `rmax · clamp((|d − focus| − range)/0.45)` — relative inverse depth is proportional to defocus — or from the distance to a planar band (tilt-shift; no depth needed). `rmax` = amount × 2.5% of the long edge. The focus is the depth at the picked point, else the mean depth under the subject mask, else the 90th percentile. A block grid of `f` px (a power of two keeping `rmax/f ≤ 16` cells), anchored to the frame like the guided filters, holds per cell the mean colour of its **out-of-focus pixels only** (in-focus pixels weigh 0, so the sharp subject never enters the blur and can't bleed into the background) times a highlight gain; an occlusion-aware gather on that grid (scatter-as-gather: a cell contributes when its own aperture — circle, six blades, or a cat's eye squeezed toward the frame centre — covers the pixel, weighted 1/r²; a cell behind the pixel spreads no wider than the pixel's own blur) is upsampled (alpha-weighted) and blended by blur size; pixels within half a pixel of focus keep their exact values. Region renders get `(rlow + 3)·f` px of apron, so tiles match. **Approximations:** the gather runs on the `f` grid (bokeh edges are about one cell soft); a blurred foreground keeps its silhouette against an in-focus background (no partial occlusion); a 1-texel ring of background around a subject stays as sharp as the subject (the nearest-tap rule).
  - **Glow** (Orton: a Gaussian of the colour, σ 0.4–3.4% of the long edge, screened over the image) and **halation** (a Gaussian of how far luma is into the highlights, σ 0.4%, added as warm red-orange light) are block-mean → Gaussian → bilinear passes on the display-referred image after the layers, before NR.
  - **Grain** is monochrome two-octave value noise added after sharpening (in the output pass, or the export tiles before their resize), strongest in the midtones, at a position fixed to the image (E frame at output scale), so tiles, regions, drafts and zoom levels agree; grain finer than a pixel is attenuated in proportion, as a downsized export shows it.
- **`ds_core::PIPELINE_VERSION`** is the single version of render output (re-exported by ds-pipeline and ds-cache, which keys cached renditions by it). A render-fingerprint test fails when output changes without a bump.
- **Lens correction** (on by default, `adj.lens`): vendored lensfun subset of every calibrated Sony E-mount lens (`data/lensfun-sony-e.xml`, CC BY-SA 3.0: 142 lenses, Sony, Sigma, Tamron, Samyang, Zeiss, Tokina) chosen by `RenderRequest::capture` (EXIF lens + focal + aperture; any of the lens's names ignoring makers, case, punctuation and parenthesized suffixes, else the shortest name a partial name's words begin, else the one lens whose words agree apart from mount/series descriptors such as "E", "FE", "Di III", Sigma year codes — "Tamron 28-75mm F/2.8 Di III RXD" ≡ "E 28-75mm F2.8-2.8"; the calibration closest to the body's crop factor; vignetting at the farthest calibrated focus distance; a calibration sensor's aspect ratio scales the distortion radius); distortion (ptlens/poly3), lateral CA per channel, and vignetting. Crops with rotation/keystone/distortion shrink automatically so the frame never shows outside-the-sensor pixels (`inscribed_crop` for the UI); straighten is clamped to ±45°. **Output size of an auto-fitted frame** (`RenderRequest::fit`, `Fit`): `FillOriginalSize` (the default, viewer and export; Lightroom's rule) keeps the size the crop has on the sensor, so an uncropped frame stays 6000×4000 (4000×6000 portrait) with lens correction or a straighten on, the inscribed area (a few percent smaller) being scaled back up in the same linear-light geometry resample; `ConstrainToSensorPixels` (the export recipe's "Constrain to sensor pixels") outputs the inscribed area at 1:1. A user crop is `crop × sensor size` either way. `fit` changes only the output scale, never what is framed: `frame_mapping` and the crop/mask maps are identical under both, so overlays are unaffected.

Decoders: the native ones (`native/`, [RAWDEC.md](RAWDEC.md): DNG, Sony ARW, Canon CR2, Nikon NEF, Pentax PEF) run first; rawler takes what they don't cover: in process with the `rawler` cargo feature (tests, `ds-rawler`), else through the separate rawler helper program when the user installed it (`ds_raw::helper`, RAWDEC.md). Without either those files are `RawError::Unsupported`.

Memory: native decoders read strips and tiles through the bounded source as they need them (uncompressed and cRAW data in parallel row bands); single-stream codecs (CR2, NEF, PEF) hold the compressed stream once. Formats that go through rawler are decoded from an in-memory copy of the file (read once through the bounded source, never memory-mapped), so a decode holds the file size in anonymous memory on top of rawler's output; keep decodes of such files sequential. `read_metadata` for non-TIFF containers reads only the first and last 8 MiB.

Previews come from the TIFF IFDs (JPEG strips and `JPEGInterchangeFormat`; DNG's compression-7 YCbCr previews; RW2's `JpgFromRaw`; ORF's maker-note preview), CR3's `PRVW`/`THMB` boxes and RAF's header JPEG; lossless-JPEG streams are never taken for a preview. Decoding goes through rawler only after the format's declared sizes are bounded (`guard`; for CR3 and RAF, `cr3::check_decodable` / `raf::check_decodable` bound the sizes rawler itself parsed, and `cr3::validate` first checks the box tree is one rawler's reader gets through, before metadata too); X-Trans RAFs and codecs rawler lacks return `RawError::Unsupported`, which the app shows as "can't develop this file yet" over the embedded preview. Per-camera results: [CAMERAS.md](CAMERAS.md).

### ds-merge
HDR merge and panorama stitching on `Frame`s: linear camera RGB before white balance, `u16`, 65535 = the clip (the layout of `ds_pipeline::denoise::linear_original`). `merge_hdr(&[HdrInput], &HdrOptions, &dyn Progress)` and `merge_panorama(&[PanoInput], &PanoOptions, &dyn Progress)` return `Merged { frame, exposure_ev, reference, ghost_regions, projection }`; everything is scaled below the clip and `exposure_ev` brightens it back to the reference frame. `quick_frame(&RawImage)` bins 2×2 for previews.
- **Registration** is a Rust feature matcher (Harris corners on a grid, bias/gain-normalized 8×8 patches, mutual ratio-test matches, RANSAC homography), chosen over Apple Vision so the same code runs in the tests, on synthetic scenes, and needs no FFI round trip per pair.
- **HDR**: frames adjacent in exposure aligned (luminance scaled to one exposure and clipped at the pair's common clip) and their exposure ratios measured from well-exposed pixels, then chained to the middle exposure, so wide brackets (±6 EV) align (EXIF only orders them, and only when every frame records the same fields; frames that still can't be aligned are reported as `unaligned`); radiance weighted by exposure with a taper before the clip; ghosts (adjacent exposures that disagree on the analysis grid) opened, dilated and split into regions, each taking one exposure (the brightest unclipped there), feathered in (a clipped sample of it keeps the merge). Pixels clipped in every frame that sees them are written at the clip on every channel.
- **Panorama**: rotation-only camera model with one focal length (EXIF 35 mm equivalent refined by a 1-D search on pairwise reprojection error), maximum-spanning-tree rotations plus refit sweeps, horizon levelling, per-frame gains from matched-point luminance; perspective / cylindrical / spherical (auto by angular extent), banded two-band blending (feathered low band, seam-cut high band; clipped samples stay out of the blend, and pixels only clipped samples cover are written at the clip, since a gain below 1 would turn a blown sky into a dim colour), auto crop to the largest covered rectangle. Lens corrections are not applied before stitching; the new photo starts with them off. Registration matches each frame with the next two in capture order (wrapping) in parallel, and every other pair only when that leaves the overlap graph in pieces; RANSAC stops early at 99 % confidence. `merge_panorama` refuses more than 60 frames. Memory is the frames (u16 RGB) plus their analysis images plus the output (at most `PanoOptions::max_pixels`, default 120 MP, 6 B/px) plus tens of MB of render scratch (2048-column tiles, reused); `ds_merge::estimate_bytes` returns it.
- The app writes the result with `ds_raw::write_linear_dng` next to the first source (`<name>-HDR.dng`, `<name>-Pano.dng`, never replacing a file) and registers it as a new photo (ds-ffi `session::merge`). Merges need one camera and one focal length. Sources decode one at a time, the frames are dropped before the DNG is written (its sensor-orientation preview develops from a downsampled copy) and the DNG streams to its temp file; previews reuse cached quick decodes per file version.

### ds-session
Session folder layout is in PLAN §4. API: `Session::create(dir, name)`, `Session::open(dir)` (rebuilds the index if missing or stale), `add_original(path, hash, meta) -> ImageId`, `variants(image)`, `load_adjustments(variant)`, `save_adjustments(variant, &Adjustments)` (atomic sidecar write + index update), ratings/tags/pick, albums and smart filters (`Filter` → query), `move_to(Selects|Trash)`, `presets` (named partial `Adjustments` + `GroupSet`), undo/redo history per variant (bounded), `GlobalIndex` (all sessions, hash lookup for dedupe).

**Search embeddings** (`embed.rs`, index v5; `images_content` indexes the sensor-data hash): MobileCLIP vectors (normalized, f16) in the `embeddings` table keyed by content identity — the sensor-data hash, else the file hash; an original not hashed yet has no key and waits — so renames, relinks, rebuilt indexes and the same photo in another session never re-embed (`embedding_jobs` also carries a vector from the file-hash key to a later sensor-hash key and prunes vectors no original uses). `search_embeddings(model, query, &Filter, RankOptions)` scores the filter's variants against an in-memory `f32` matrix (dropped on embedding writes and when another connection committed, by `PRAGMA data_version`; the image→row map is rebuilt after any other write, by `total_changes`); `similar_to` excludes the photo's own original. `GlobalIndex` v2 adds `search_items` (session, path, key) and shared `embeddings` for `search` across sessions, cached until its `search_generation` changes (any items change, a rename; an unchanged re-sync writes nothing; one that drops originals — trashed, removed as missing — drops their vectors unless another item uses them). `forget_search` (removed from the app's list) and `unregister_session` also prune vectors no session's items use. Ranking (`ds_core::embedding::rank`): top `limit`, score ≥ `min_score` and within `window` of the best.

### ds-c1
Capture One session import, read-only on the C1 side (format notes: `docs/C1_FORMAT.md`).

- `map_variant(settings, original, meta, wb, keyword_library) -> Mapped`: rating, colour tag, keywords, white balance (through an injected `WbConverter`), exposure, HDR and crop/straighten, plus the edits with no translation and why.

### ds-lr
Lightroom Classic and Camera Raw import, read-only on the Adobe side (format notes: `docs/LR_FORMAT.md`, which lists what is unconfirmed).
- `read_catalog(path, cancel) -> LrLibrary` (the `.lrcat` is copied to a temp dir and the copy opened; only real tables are queried; time limit, cancel interrupt), `read_sidecars(folder, cancel) -> LrLibrary` (`.xmp` files and DNG-embedded XMP), `read_presets(path, cancel) -> Vec<LrPreset>` (`.xmp` and `.lrtemplate`). Develop settings are read into `Develop` (name → `Setting`) by a safe Lua-table parser and the XMP reader, both depth- and size-limited.
- `map_develop(&Develop, &MapContext) -> Mapped`: Lightroom's non-default settings onto an `Adjustments` (global tools, colour editor, curves, crop with the user's rotation, and masks as `Lightroom: …` layers), the categories touched, what mapped (exact or approximate) and what has no equivalent.
- `import(&mut Session, &LrLibrary, &ImportOptions{dry_run, overwrite_edits, categories}, cancelled) -> ImportReport`: matches photos by path, content hash, then name and capture time; a three-way merge per field and per develop category against `<store>/.ds/settings/lightroom-import.json` (idempotent, Darkslide edits kept unless asked); virtual copies become variants; plain collections become albums.
- `revert(&mut Session) -> Option<RevertReport>` / `can_revert`: take back the imports since the last revert from `<store>/.ds/settings/lightroom-import-undo.json`.
The state and journal are separate from ds-c1's (their types are C1-specific); the diff/fold logic is a copy of ds-c1's.

**Library** (`library.rs`, global index v6): one `library_items` row per variant of every session, synced by diff from the session (`Session::library_records`, `GlobalIndex::sync_library`); queries on an in-memory copy (`library_query` → ordered ids, `library_items` pages details); collections and smart collections across sessions; rating/label/flag edits written through to the owning session's sidecars (`apply_library_edit`, then `library_patch`). See FFI.md §Library.

**Find** (`find.rs`, global index v4): one `find_items` row per original of every session (path, content key, capture time, best rating, first variant's flag, keywords, people tagged, people suggested by face matching, location fields, its variants' titles and captions; v4 added `titles`, filled by each session's next sync), replaced per session by `sync_find_items` (no write when unchanged). `GlobalIndex::find(&FindSpec)` scans an in-memory copy (folder names, keywords, people and locations interned once; rebuilt when the search generation moves) with the search vectors: people, places that resolve (a session name, a folder in the path, a keyword, a location field, whole words, accents folded), date (`ds_core::date::DateFilter`), rating and flag are hard filters; the text's similarity ranks (floor and window as search), a place nothing is called ranks as "looks like" (a boost under a text query), an unknown person's name only boosts photos whose folders or keywords contain it. A description found word for word in a title or caption (`MatchReason::Title`) keeps the photo whatever its visual score, or without a vector, and adds a small bonus. Each hit carries its `MatchReason`s; sessions come back when their name, a folder or a keyword matched, or when they hold ≥ 3 hits. Queries come from `ds_ai::find` (`RuleBasedFindParser`: deterministic, the edit seam's shape).

**Metadata** (index v7): the IPTC Core fields (`ds_core::IptcMeta`: title, caption, creator, copyright, credit, headline, city, state, country, sublocation, instructions, usage terms) are the sidecar's `iptc` (additive, SIDECAR_SCHEMA_VERSION 1; every field always written, so clearing one sticks), set by the undoable `Session::set_iptc`, mirrored into `variants.iptc` (JSON, `''` when empty), and the title and caption join `variants.search`. A v6 index gains the column in place and re-reads its sidecars. New originals start with the camera's EXIF `Artist`/`Copyright`, overlaid by the file's own XMP packet and then its XMP sidecar (the sidecar wins; on a card import, the sidecar beside the card's file; each folder listed once per batch; language alternatives take `x-default`), then an import's metadata preset. Exports write them as XMP (`dc:title`, `dc:description`, `dc:creator`, `dc:rights`, `photoshop:*`, `Iptc4xmpCore:Location`, `xmpRights:UsageTerms`), IPTC-IIM in JPEG (2:05…2:120; usage terms are XMP only) and EXIF `ImageDescription`/`Artist`/`Copyright`; the photo's creator and copyright win over Settings' artist/copyright, which fill them when empty. Removing the location (strip GPS) also drops city, state, country and sublocation; the EXIF caption is capped at 2000 bytes and an XMP packet too large for one JPEG segment is left out (IIM still carries the fields).

**People** (index v6, `faces.rs`, `people.rs`): faces (box, capture quality, f16 vector per content key and face model) and `face_scans` are derived; who is on a photo is the user's answer in the sidecars (`people`, `people_rejected`: name, people-store id, face box; additive, SIDECAR_SCHEMA_VERSION 1), mirrored into `variant_people`; unnamed merges/splits are `face_links` (index data: a rebuilt index forgets them, never a name). Names live in the app-level `PeopleStore` (`people.json`, atomic, never replaced when unreadable). The global index keeps every session's faces and recomputes each photo's suggested people when faces or the store change (`refresh_suggestions`), so Find matches a named person in sessions that are offline. `ds_ai::faces::cluster`: average linkage by nearest-neighbour chain (O(n²) time and memory, parallel similarity matrix), must-links pre-merged, cannot-links −∞. **Places** (`locations`, derived): XMP/IPTC location names and GPS per content key, re-read when its XMP sidecar changes. **Map** (index v8, `map.rs`): a variant's `geotag` (sidecar, additive; mirrored into `variants.geo_*`) wins over the original's GPS; each find row carries the position (global index v5, `find_items.lat/lon`) and `GlobalIndex::map_points` lists every session's located originals. **AI Cull notes** (index v9): why AI Cull rejected a variant (`ds_ai::explain_reject` → `reject_note`) is sidecar `cull_note` (additive, `null` when cleared), mirrored into `variants.cull_note`; `set_pick` clears it, so it only ever describes a reject that still stands.

### ds-cache
Disk cache under `<session>/.ds/cache/`: thumbnails (512 px JPEG) and previews (2560 px JPEG), keyed by variant + adjustment hash. In-memory LRU (byte-bounded). `JobScheduler` with priorities `Visible > Prefetch > Background`, cancellable, bounded worker pool; UI requests jump the queue.

### ds-import
`scan_volume(root) -> Vec<Candidate>` (DCIM walk, supported types, sidecar pairing e.g. same-name .JPG), `plan(candidates, dest session, rename template, dedupe lookup)`, `run(plan, progress) -> ImportReport`. Copy = read once → write `.partial` + BLAKE3 in the same pass → fsync → re-read and verify hash → rename. Journal file allows resume. An optional second destination is written in the same pass.

**Journal and leftovers** (`journal.rs`, `fsio.rs`): one journal per set of source volumes, `<dest>/.ds/import-journal-<id>.json`, written atomically; the whole plan is recorded `Pending` before the first byte, entries become `Done` only at a `F_FULLFSYNC` checkpoint, and the journal is removed once an import finishes complete. Its paths are untrusted (the folder may be synced or restored): absolute, `..` or empty destination paths and a relative backup root reject the journal. The format version (`JOURNAL_VERSION`) is read before the rest: a torn, unsafe or **older** journal is renamed to `import-journal-<id>.bad-<ts>.json` and ignored (never deleted; its files are then "not ours" and only reused after re-hashing); a **newer** one (a later Darkslide, then a downgrade) is skipped but left in place, and a run whose own journal is newer fails with `ImportError::JournalVersion` rather than rewriting it. Partials (`.<16 hex>.partial` beside the final name): those an earlier run recorded in our journal are removed before copying; a partial no journal knows is left alone while fresh (another import may be writing it, so that file fails) and cleared once untouched for `STALE_TEMP_AGE` (1 h); a torn final file of ours is moved to `<root>/.ds/quarantine/<stamp>/`, never deleted.

**Hashing is I/O-bound and stays on the CPU** (`benches/hash.rs`, six A9 ARWs, M4 Pro under load): one BLAKE3 hasher (one `Hasher` per file, 4 MiB chunks, on the reader's helper thread) runs at 1.6–2.2 GiB/s, three files at once (`concurrency: 3`) at ~5.8 GiB/s; a sequential uncached (`F_NOCACHE`) 4 MiB read stream from the internal SSD delivers 4.1–4.8 GiB/s, and the A9's SD UHS-II card ≤ ~0.3 GB/s. A single hasher is 5–7× faster than the card, so the copy is card-bound; the verify re-read of one file is hash-bound (~25 ms for a 48 MB ARW) but overlaps the other workers' card reads. A GPU would not help: data arrives in 4 MiB chunks of a sequential per-file stream, and if SSD-to-SSD imports ever outrun the hashers, `blake3`'s multithreaded `update_rayon` on large chunks is the lever, not a device round trip.

### ds-archive
`ArchiveTarget { path, excludes }` (a missing target folder on a mounted, writable volume is created one level at a time below its existing ancestor — never the mount point; `TargetUnavailable` = volume not mounted ("offline"), `TargetNotUsable` = permission problem, a file in the way or a relative path), `Scheduler` (interval + debounce + on-demand), runs `rsync` (prefers `/opt/homebrew/bin/rsync` 3.x, falls back to `/usr/bin/rsync` openrsync) with `-a --partial --backup --backup-dir`. Never `--delete`. Exclude patterns (defaults, and one anchored pattern per rejected original) go through an `--exclude-from` file, never one argument each. The archive mirrors a managed session's current layout (`ArchiveTarget::mirror_folders` = `Capture`, `Selects`): before rsync, a file archived under one folder that the session now has only under another is renamed there on the target (or, if the target already has it there, moved into that run's backup dir), so Move to Selects never leaves a duplicate; files the session has in neither (rejects moved to its Trash) stay where they are. Nothing is deleted. The mount is re-checked before every create and move (`check_mounted`: `statfs` mount point, case-insensitive `/Volumes`). The volume a target is on (`VolumeId`: mount point, source, fs type from `statfs`; `archive_volume_identity` in ds-ffi) is recorded when the user confirms it (`ArchiveConfig::target_volume`); every check and run requires the target to be on that volume, so a share mounted outside `/Volumes` that went away (the path now on the boot disk) is offline and nothing is created. Without a recorded volume, a missing target folder outside `/Volumes` is never created; a target deliberately on the boot disk is recorded there and works. Takes a consistent SQLite snapshot before each run. Status: last success, pending count, last error. **Amazon Photos backup** = mirror originals into a folder watched by the official Amazon Photos app (hardlink/clone where possible, else copy), tracked in a manifest.

### ds-export
Recipes: format (JPEG q, TIFF 16, PNG, HEIC via Swift ImageIO hook), long-edge size, output space, sharpening for output, filename template, destination (session Output/ or custom). EXIF copied from the original (keeps capture time/camera/lens). Parallel across images, bounded memory.
The injected `Renderer` renders full resolution (`render`); all recipes of one output space share that render and are resized (linear light) and sharpened on the CPU. A renderer that can resize and sharpen itself — the GPU pipeline (per-stripe GPU resize + `RenderRequest::output_sharpening`) — implements `render_sized(item, recipe) -> Option<Result<Rendered, String>>`: a recipe alone in its output space is then rendered directly at `recipe.target_size(..)` with `recipe.sharpen` applied, with no full-resolution readback (144 MB at 16-bit for an A9 frame) and no CPU resize (21 ms to 2560 px) or sharpen. Several recipes per space still share one full render: a second full-resolution develop costs more than the CPU resizes.
Sized renders for JPEG (mozjpeg) and PNG8 are developed as 8-bit RGBA (`OutputFormat::Rgba8`, packed on the GPU) and encoded as is (`Pixels::Rgba8`; mozjpeg reads RGBX rows directly); TIFF16, PNG16, HEIC and the app's JPEG hook stay 16-bit. JPEG/HEIF/PNG/TIFF originals are sized by the app (ds-ffi `ImageEncoder::upright_size` + `decode(.., target)`: ImageIO decode, Core Image orient and colour management, Metal passes with this crate's resize and sharpen math; ΔE2000 mean 0.02 against the CPU path); upscales, no GPU or an unreadable header take the full-size path.
**Soft proofing** (`proof.rs`, Little CMS via `lcms2`, built from its vendored source): `proof_lut` bakes a proof into a 33³ table over the working gamut (Rec.2020, sRGB-encoded) — the colour shown (Rec.2020 → profile with the chosen intent and BPC, 16-bit device values, → back relative colorimetric, linear Rec.2020) and, in alpha, the signed distance to the profile's gamut surface in cells (positive outside). A colour is out of gamut when its relative-colorimetric round trip moves it by more than 1 ΔE76 (matrix/TRC profiles) or 5 (any profile with A2B/B2A/D2B LUTs, hybrids included: Little CMS's own threshold); every grid edge crossing the surface is bisected (12 steps), so the interpolated zero crossing sits on the surface; a gray profile's gamut is a line (the neutral axis, thinner than a cell), so for it the shader tests encoded chroma (max − min) against a tolerance bisected from the exact test instead of alpha (a 25³ sweep of the working gamut agrees with the exact test on ≥ 99.5% of colours, and nothing comfortably inside sRGB is flagged). Transforms are unoptimized (`NO_OPTIMIZE`); the shown colour is still trilinearly interpolated, so at saturated edges it can be off by a fraction of a cell. While proofing, the viewer renders `Rgba16fLinearRec2020` frames (pipeline `OutputSpace::Rec2020` with the f16 format), so colours outside P3 are proofed and gamut-checked as themselves; the shader does one hardware-filtered 3D texture read and paints the warning where alpha > 0. The clipping warning and the loupe's clip flag judge the colour in the surface's primaries, so a working-gamut frame's colour that clips to 0 there is marked. A slider drag at the 5K fit (Draft, 2832 px, GPU) costs the same with the proof's f16 Rec.2020 frames as with 8-bit sRGB on an SDR display (11.8 vs 12.5 ms, `benches/render.rs` `proof_drag_gpu_draft_2832`). Renderers without float frames fall back to 8-bit frames (P3-clipped). Build (with the surface bisection): 26.4 ms (sRGB), 34.9 ms (Generic CMYK, a LUT profile), off the main thread; one build at a time, intermediate settings skipped. Into a matrix/TRC profile, colours outside it are first soft-compressed (`ds_core::gamut::compress`, the pipeline's own output compression, through the profile's colorants) in the export and in the proof, so "Use Proof Profile (sRGB)" matches a plain sRGB recipe instead of clipping channel by channel; LUT profiles use their own tables. A recipe's `output_profile` (RGB only; linear-light profiles need a 16-bit format) renders 16-bit Rec.2020 (`OutputSpace::Rec2020`; raster originals decode in P3 and are converted) and converts to the profile (same intent and BPC, `HIGHRES_PRECALC`, rayon by 64-row chunks; 27 ms for a 6000×4000 16-bit frame) before encoding, and embeds it; the precalculated grid can differ from the proof's exact transform by its interpolation error near the gamut surface. ImageIO (HEIC, the hardware JPEG) refuses a profile it can't make a colour space from rather than tagging the pixels sRGB.
**Watermarks** (`watermark`, `ExportRecipe::watermark`): a text line or a PNG logo is drawn last, on each output at its final size (after resize and output sharpening, on every path: CPU, GPU-sized 8-bit and 16-bit renders), never on a full render shared between recipes. Sizes are fractions of the output (text em of the short edge, logo width of the width, margin of the short edge), so the mark keeps its relative size and place at every export size; text too wide for the frame is rasterised again smaller. Text is rasterised by the app's Core Text (`TextRasterizer`, ds-ffi `WatermarkTextRenderer`) as an 8-bit coverage mask: the system's fonts, kerning and glyph fallback without a Rust font stack; colour, a box-blurred drop shadow, opacity and placement are done here. Colours are converted into the output space (sRGB colours and logos to Display P3 for P3 outputs) and a logo is resampled premultiplied in linear light, but the "over" blends in the output's encoded values, as Lightroom and Photoshop do (50% white over black ≈ 128/255); compositing runs row by row over the mark's rectangle only (a logo is Catmull-Rom resampled one output row at a time), so it allocates no image-sized buffer. Logos are kept as decoded 8-bit RGBA (4 bytes a pixel, ≤ 4096²) and linearised per filter tap; ds-ffi caches them per file version, bounded to 128 MB. Text that is blank once its tokens are filled in (`{copyright}` and no copyright) is left out and reported per file (`ExportedFile::watermark_skipped`). `watermark_preview` draws the recipe editor's preview with the same code; the app calls it off the main thread, debounced, with the credits the export uses (Settings', else the photo's EXIF), and loads the preview photo only when a watermark is shown.

**Post-process seam** (`post.rs`, `ExportRecipe::post_process`): steps drawn on each output at its final size, after resizing and output sharpening, on the working copy (never a full render shared between recipes), on the 8-bit sized path and the 16-bit path alike: plug-in steps (ds-ffi `PluginStep`, WebAssembly through ds-plugin) in the recipe's order, then the watermark last (`WatermarkStep`, the native provider). A step may grow the canvas (`layout`: new size and where the image goes; the margin starts black and opaque; each later step gets the photo's rect). Every call is isolated (`catch_panic`); any failure is that file's `ExportError::PostProcess`, and nothing is written.

### ds-plugin
The plug-in host (docs/PLUGINS.md).
- **Packages** (`package.rs`): a `.dsplugin` folder or zip is read once into memory (regular files only, no symbolic or hard links, ASCII names unique ignoring case, dotfiles and `__MACOSX` ignored, ≤ 512 files / 64 MB, zip names checked before inflating); hashing, the signature, parsing and compiling all use those bytes.
- **Manifest** (`manifest.rs`): format 1; unknown keys are load warnings and author-time errors (`parse_with(strict)`); a contract range per kind (`CONTRACTS`); typed params; plug-in text cleaned and capped (`text.rs`), names that pass for Darkslide refused; permissions (`files.*`, `network:`, `account:` are sensitive); `[accounts]` with `api_hosts`, and well-known account names tied to their services' sign-in hosts.
- **Registry** (`host.rs`): bundled folders load only when their files equal the hashes compiled in by `build.rs` from `plugins/builtin` (no signing key exists); `darkslide.*` ids are reserved both ways; the signer is pinned per id in `state.json` (another key, or signed ↔ unsigned, is a different plug-in: refused at install, an error when dropped in by hand, never inheriting grants); clashes resolve to a development folder, then the higher version, then the managed copy; installs go through `Plugins/.staging-*` and the staged copy is what the sheet shows and what is renamed into place; downgrades need consent, a changed same version is refused; `forget` drops grants, pins and any copy an update kept aside after a removal; unlinking a development folder drops its `dev:<id>` decisions; `files.*` grants take a folder that may not be, contain or lie inside the support folder, the app, plug-in folders or any session (`check_folder`, re-checked at use); unsigned or untrusted code never gets files, network or accounts unless "Allow unsigned code plug-ins" is on (and loses them when it goes off); development folders load in place but are checked against an installed id's pinned signer, and keep their decisions under `dev:<id>`; staged copies expire after 30 minutes, the pin is re-checked at install, and only stagings older than that are cleaned at open.
- **Data packs** (`pack.rs`): `look@1` (amounts only, so Intensity is exact), `style@1` (groups, relative and absolute explicit), `phrases@1` (with a language), checked against `ds_core::edit_keys` (key, kind, range); an item with something unknown is left out ("needs a newer Darkslide"); third-party look ids are `<plugin-id>/<id>` and their UUIDs are derived.
- **Runtime** (`wasm.rs`): wasmi 2 with loop dispatch and multi-memory off; one instance per image on an 8 MB-stack scoped thread; one 64 MB memory and one table of ≤ 100 000 elements per instance and a global 512 MB budget (`MemorySlot`, at most eight at once); fuel on every entry (10 M for setup calls, 5 M + 400 per pixel per strip); pixels in strips of ≤ 4 MB plus the declared apron, only each strip's own rows copied back (the apron above a strip comes from a copy of the input rows, so results don't depend on the strip height); a slot wait gives up on Cancel; `ds_output_layout` for a bigger canvas (≤ 100 MP, and `post::MAX_CANVAS_GROWTH`: at most twice the image's area across all steps); imports limited to `log`, `error`, `progress`, `photo_rect`, `param_*`; three failures in a row suspend a contribution until relaunch; the export's Cancel reaches `progress()` through a 10 ms watcher. Unsigned code runs only after its own Allow (`allow_unsigned`, reset by any unsigned update) or with the authors' global switch; the signature covers the signer's claimed name; an install interrupted between its two renames is restored from `.replaced/` at the next open; stored params an update no longer allows are clamped (`params::resolve_lenient`).
- **Destinations** (`destination.rs`): the `export_destination` contract is specified (types, `check_request`: granted HTTPS hosts, host-only headers, job file handles, the account's token only to its `api_hosts`; redirects drop the token on a host change; Keychain naming); nothing runs through it yet.
- `cli.rs` is the `ds-plugin` binary (`new`, `validate`, `pack --out|--zip`, `keygen`, `sign`, `contracts`).

**Edit vocabulary** (`ds_core::edit_keys`): every `EditCodec` key with its group, kind and range — one table for the plug-in validator, exported over FFI (`edit_keys()`) so a Swift test fails when the app's `EditCodec` drifts from it.

### ds-gphotos
Google Photos export destination, self-contained behind one seam so it can become a plugin: `Transport` (one blocking request → response; `URLSession` in the app via ds-ffi's `GphotosHttp`, `mock::MockGoogle` in tests, feature `mock`). `oauth`: installed-app OAuth with PKCE S256 and a loopback redirect (`http://127.0.0.1:<port>/`, the only redirect Google allows for Desktop clients), `code_from_redirect` checks `state`; scopes `photoslibrary.appendonly` + `photoslibrary.readonly.appcreateddata` (since March 2025 an app sees and adds to only what it created). `Client`: one refresh on 401; 429/5xx/no answer retried with exponential backoff (≥ 30 s after a 429, `Retry-After` honoured, `Sleeper` seam); resumable uploads in chunks rounded to the server's granularity, a failed chunk resumes at `X-Goog-Upload-Size-Received` and an ended session starts over; albums listed/created, `find_or_create_album` reuses by title; `batch_create` ≤ 50 items, per-item results (200/207). `upload`: files → album, `batchCreate` every 50 uploaded files, serially; per-file failures; a sign-in or rate-limit failure stops the job and fails the rest with that reason; cancel between requests. The OAuth client is built into Info.plist by `scripts/build-app.sh` from `DS_GOOGLE_CLIENT_ID`/`_SECRET` or the git-ignored `secrets/google-oauth.json` (never committed); a user's own client in Settings overrides it. The app uploads a recipe's outputs after the export batch (`ExportModel.uploadToGooglePhotos`), one recipe at a time. Setup: docs/GOOGLE_PHOTOS.md.

### ds-ai
Cull scoring from pixels (sharpness via variance of Laplacian on a luma preview, focus-region sharpness, exposure clipping, noise estimate), near-duplicate/burst grouping (perceptual hash + capture-time gaps), a combined `CullScore`, and merging of Vision-provided signals (eyes open, face count, aesthetics score). Includes a natural-language edit parsing seam: text → typed `EditIntent` → `Adjustments` delta.
```rust
pub fn analyze(img: &LumaImage, cfg: &AnalysisConfig) -> ImageAnalysis;            // CPU reference, single-threaded
pub fn analyze_with_subject(img, cfg, subject: &[SubjectRegion]) -> ImageAnalysis;
pub fn analyze_batch_cpu(images: &[LumaImage], cfg) -> Vec<ImageAnalysis>;       // rayon across images
pub struct GpuAnalyzer;  // Send + Sync; wgpu/Metal
impl GpuAnalyzer {
    pub fn new() -> Result<Self, GpuError>;                  // Err(NoAdapter) without a GPU
    pub fn with_config(cfg: AnalysisConfig) -> Result<Self, GpuError>;
    pub fn analyze_batch(&self, images: &[LumaImage]) -> Vec<ImageAnalysis>;
    pub fn analyze_batch_with_subjects(&self, images: &[LumaImage], subjects: &[Vec<SubjectRegion>]) -> Vec<ImageAnalysis>;
    pub fn is_available(&self) -> bool;                      // false once a rebuilt device failed too
    pub fn trim(&self);                                      // drop pooled chunk buffers
}
pub enum Analyzer { Gpu(GpuAnalyzer), Cpu(AnalysisConfig) }  // Analyzer::new(cfg): the GPU when available
```
- **Batched GPU analysis** (`src/gpu/`): every full-resolution reduction runs on the GPU in integer arithmetic — per-tile and per-subject-block stencil sums (Laplacian, Sobel tensor, luma moments, clips; one workgroup per ≤ 256 px rectangle, 4 pixels per `vec4<i32>`, exact 64-bit workgroup reduction), pHash/dHash box sums with the exposure histogram (one workgroup per box row), and the noise residual histograms at 1–4 px spacings on the flattest tiles (a second submission, after the tile sums pick the tiles). The CPU finishes with the *same code* as `analyze` (tile ratios, focus region, medians, 32×32 DCT: ~54 µs of a 2.95 ms analysis; the DCT alone 1.4 µs, cheaper than a dispatch), so **results are bit-identical** to the CPU reference: `tests/gpu_samples.rs` checks every per-tile value, group, pick and cull reason on real A9 bursts (max relative difference 0).
- **Throughput** (criterion `analyze_batch_*`, real A9 previews, M4 Pro shared with other work): batch 1 / 8 / 64 / 256 = 0.67 / 2.3 / 9.6 / 37.9 ms on the GPU vs 2.9 / 25.8 / 206 / 827 ms single-thread and 3.0 / 4.3 / 27 / 109 ms rayon (64: 21.6× single-thread, 2.8× rayon).
- **Memory**: chunks of ≤ 128 MiB luma, ≤ 256 images, ≤ 2¹⁹ stencil rectangles (≈ 125 MB of buffers for 64 previews, ≤ ~220 MB worst case); on unified memory the luma is copied straight into a mapped storage buffer. Buffers are pooled per concurrent caller (one idle set kept; `trim` drops it). No lock is held while a chunk runs, so calling from rayon tasks is safe.
- **Failure**: a device error, loss, timeout or panic in a chunk → that chunk runs on the CPU and the device is rebuilt before the next; a rebuilt device that fails before completing a chunk leaves the analyzer on the CPU. Empty images, images longer than 2²⁴ px and images too large for one chunk always run on the CPU.
- **Match Total Exposures** (`matching`, driven by ds-ffi `matching.rs`; Edit ▸ ⌥⇧⌘M, Lightroom's binding, since ⌥⌘M is the Window menu's Minimize All): the focused photo is the reference. Each frame is rendered at ≤ 512 px (`Priority::Tool`, shared GPU renderer or the CPU fallback, linear Display P3) and metered as the centre-weighted median luminance (corners weigh ¼) of the pixels that are neither output-clipped nor black. Sensor clipping is handled with a 64 px fully clipped probe frame rendered with the same edit: reference and target are both metered below 0.9 × the lower of their two clip levels, so a bracket pushed into clipping meters like the unclipped reference and a blown region only one frame has is left out. The tone curve isn't linear, so each target is re-rendered with candidate deltas (secant steps, ≤ 5 renders, tolerance 0.02 EV; an overshoot into unreliable metering is halved back). EXIF (shutter, aperture, ISO + both exposure sliders) is the fallback when fewer than 20% of the weighted pixels are usable, and flags a > 3 EV disagreement. The app adds the deltas to the targets' exposure (clamped to ±5) as one undo step. Same-scene synthetic brackets (−2.5…+1.5 EV, ±0.1 EV), a blown quarter (±0.1 EV) and a real A9 frame scaled −1.3 / +0.7 EV (+1.296 / −0.696) are tested. "Match White Balance to Focused Photo" sets each target to the reference's Kelvin/tint (As Shot read through the camera matrix from the tags on both sides; a target already within 0.5 K / 0.05 tint is left alone), one undo step. Layers with AI masks are metered without their Vision masks (the metering render has no `MaskSource`): such a layer then affects the meter as if its AI shape were empty, so a set edited mostly through AI-masked layers matches on the global edit; the other mask shapes render as usual. A metered delta that disagrees with EXIF by more than 3 EV is still applied and called out in the toast. A match decodes a photo the viewer hasn't cached without adding it to the decoded-RAW cache, and drops its renderer caches once it is metered, so a large set doesn't evict the photos on screen. Both matches are cancellable (between renders / between targets) and bound to the session they started in: opening another session cancels them, and results are applied only to photos still in that session.
